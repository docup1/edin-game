# API игры

Документ описывает внешний API, состав SQL-функций, содержимое кэша и события.
Реализации здесь нет - это черновик контракта.

## Диаграммы

Четыре sequence-диаграммы в `diagrams/`, все рисуются в mermaid.

| Файл | Что показывает |
|---|---|
| `auth.mmd` | Вход через OIDC, справочники и общий поток состояния |
| `lobby.mmd` | Всё до игры: список, создание, настройки, отмена, вход, старт |
| `game.mmd` | Всё во время игры: ход, разбор стойл, обрыв связи, пропуск, выход |
| `admin.mmd` | Библиотека карт |

**Правило размещения не про `{game_id}`, а про смысл.** Всё, что
происходит в идущей партии, живёт в `game`: и ход, и технические вещи -
обрыв связи, пропуск, выход. Всё, что до игры - создание, настройки,
вход, старт - в `lobby`.

Поэтому `POST /api/games/{game_id}/password` лежит в `lobby`, хотя роль
админа обычно означает `admin`. Пароль ставят до игры, значит и разбираться
с ним - до игры.

На каждой стрелке диаграммы стоят коды ответов и краткая форма. Полный JSON
живёт здесь, в `API.md`: на диаграмме он превращал бы её в простыню.

## Участники

| Кто | Что делает |
|---|---|
| Пользователь | Играет, видит интерфейс |
| Клиент | Приложение в браузере: держит cookie, рисует состояние, принимает события |
| Сервер | Единственный, кто ходит в базу. Проверяет правила, ведёт SSE |
| Кэш | Память процесса: сессии, состав лобби, чей ход, подключения SSE |
| БД | PostgreSQL: источник истины, хранит всё, что переживает рестарт |

Прямого доступа клиента к базе нет. Кэш можно потерять - после перезапуска
сервера клиенты войдут заново, а состояние партий восстановится из базы.

## Ошибки

Единый формат на все ответы с ошибкой:

```json
{ "error": "не_ваш_ход", "message": "Сейчас ход другого игрока" }
```

| HTTP | Когда |
|---|---|
| 401 | Нет или просрочена сессия |
| 403 | Нет прав: не ход, не создатель, не тот игрок |
| 404 | Партия или карта не найдена |
| 409 | Состояние не позволяет: не ваш ход, партия уже идёт, место занято |
| 422 | Правило не выполнено: нечем ходить, нет места в стойле |

## Авторизация

| Метод | Путь | Возвращает |
|---|---|---|
| GET | `/api/auth/login` | `{ "url": "ссылка на страницу входа провайдера" }` |
| GET | `/api/auth/callback` | `Cookie sid` + `{ "user_id": "uuid" }` |

Провайдер входа - внешний, клиент по ссылке уходит к нему и возвращается
с кодом. Токен провайдера наружу не отдаётся, наружу только своя cookie.

Сервер берёт из токена не только `user_id`, но и роль - `user` или `admin`.
Роль кладётся в сессию в кэше. Отдельной таблицы админов в базе нет, и
не требуется: `/api/admin/*` проверяет роль в сессии и отвечает 403,
если роль не `admin`.

Все остальные эндпоинты требуют эту cookie. Cookie - `HttpOnly`, `Secure`,
`SameSite=Lax`. Сессии живут в кэше, в базе нет ни таблицы пользователей,
ни таблицы сессий.

## Партии

### До игры

Всё это - `lobby.mmd`.

| Метод | Путь | Отвечает |
|---|---|---|
| GET | `/api/games` | `200` `{ items: [...], total }` |
| POST | `/api/games` | `201` `{ game_id, player_id, is_host }` |
| PATCH | `/api/games/{game_id}` | `200` `{ game }` |
| DELETE | `/api/games/{game_id}` | `204` пусто |
| POST | `/api/games/{game_id}/password` | `204` пусто, только админ |
| POST | `/api/games/{game_id}/join` | `200` `{ player_id, hand, is_host }` |
| POST | `/api/games/{game_id}/start` | `200` `{ game_id }` |

| Метод | Путь | Тело | Ошибки |
|---|---|---|---|
| GET | `/api/games` | - | 401 |
| POST | `/api/games` | `{ "name", "max_players", "password"? }` | 401, 422 |
| PATCH | `/api/games/{game_id}` | Любые из `name`, `max_players`, `password` | 401, 403, 404, 409 |
| DELETE | `/api/games/{game_id}` | пусто | 401, 403, 404, 409 |
| POST | `/api/games/{game_id}/password` | `{ "password" }` | 401, 403, 404, 409 |
| POST | `/api/games/{game_id}/join` | `{ "password"? }` | 401, 403, 404, 409, 422 |
| POST | `/api/games/{game_id}/start` | пусто | 401, 403, 404, 409 |

### Параметры списка

Только у `GET /api/games`. Остальные списки - только админские.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `has_slot` | `1` | Только партии со свободными местами. `0` - показать все |
| `mine` | `0` | Только партии, где игрок уже сидит |
| `limit` | `50` | Сколько вернуть, максимум 200 |
| `offset` | `0` | Сколько пропустить |

Фильтр по свободным местам стоит по умолчанию не просто так: гость видит
список, кликнет в партию без мест и получит отказ. Спрятать пустые дешевле,
чем объяснять.

Пароль - это тело, а не query-параметр. Он может быть длинным, в логах и
истории браузера query-строка остаётся навсегда, а тело - нет.

### Состав партии

Отдельного `GET /api/games/{game_id}` нет, и это осознанно. Гостю нужно
знать, есть ли место и пусто ли, а это уже есть в полях списка:

```json
{ "items": [ { "id": "...", "name": "Пятница", "seats": 6,
               "occupied": 3, "needs_password": true } ],
  "total": 1 }
```

Свойств «кто именно сидит» в списке нет. Гость всё равно не имеет права
их видеть, а создатель узнает состав из потока, где он и так получает всё.

### `PATCH`, `DELETE` и пароль

`PATCH` и `DELETE` - только создатель и только пока партия не началась,
иначе 409. `max_players` нельзя сделать меньше, чем занято мест: иначе
оказалось бы, что кто-то лишний. Пароль можно обнулить, передав `null`.

`POST .../password` - тоже только до старта, но роль `admin`. Пароль,
поставленный админом, создатель снять не может: снять его можно тем же
эндпоинтом.

**Почему `DELETE` означает отмену.** Связанные с партией строки удаляются
вместе с ней, это осознанное удаление. Убирать партию из списка, ничего не
удаляя, пришлось бы делать флагом `cancelled` и вечно о нём помнить.

### Про `join`

`join` отказывает, если партия началась **и за игроком нет своего места**.
Своё место - это и есть тот случай, когда игрок выходил через `leave` и
вернулся. Место за ним сохранилось, поэтому вернуться можно, и рука
придёт пустой: карты ушли в сброс.

Если же место свободное, а партия уже идёт - 409. Дописаться в начавшуюся
партию нельзя, это была бы игра с дырой в середине.

### Про `start`

`start` и отмечает вызвавшего готовым, и запускает игру, если готовы все.
Отдельного `ready` нет: readiness - это не действие, а факт, и он живёт
в кэше вместе с составом лобби. Если игроков трое, а готовы двое, ответ
`409`, и готовность не сбрасывается - ждём третьего.

### Во время игры

| Метод | Путь | Отвечает | Ошибки |
|---|---|---|---|
| POST | `/api/games/{game_id}/event` | `204` пусто, состояние приходит в поток | 401, 403, 404, 409, 422 |
| POST | `/api/games/{game_id}/end` | `204` пусто, новый ход приходит в поток | 401, 403, 404, 409 |
| POST | `/api/games/{game_id}/leave` | `204` пусто | 401, 403, 404, 409 |

**Почему у `event` и `end` пустой ответ.** Состояние приходит в поток, а
дублировать его в теле ответа значило бы отправить его дважды. Тело нужно
только для ошибок.

**Про `leave`.** Игрок не выбывает: место за ним сохраняется, карты
возвращаются в сброс, рука становится пустой. На своей очереди он просто
доберёт карты и продолжит. Выбывания в API нет.

Ошибки: `401` без сессии, `404` если партии нет, `403` если игрок в этой
партии не состоит, `409` если партия уже закончилась. Выход не требует его
хода, поэтому `403` тут означает именно «не участник», а не «не ваш ход».

## Ход

Всего два эндпоинта. Карты выбирает игрок, механики применяет сервер.

| Метод | Путь | Возвращает |
|---|---|---|
| POST | `/api/games/{game_id}/event` | Пусто. Новое состояние приходит в поток |
| POST | `/api/games/{game_id}/end` | Пусто. Новый ход и состояние приходят в поток |

### Как проходит ход

1. Сервер объявляет в потоке, что ход открыт, и присылает список доступных
   операций.
2. Игрок отправляет **один или несколько** `event` подряд. Каждый
   применяется сразу, поэтому следующий видит уже изменённое состояние.
3. Игрок отправляет `end`, и сервер закрывает ход.

Ответ пустой не потому, что серверу нечего сказать. Состояние приходит
в поток, а дублировать его в теле ответа значило бы отправить его дважды.
Тело ответа нужно только для ошибок.

### Одно событие на запрос

```json
{
  "turn": 12,
  "request_id": "01J8ZC4K2Q",
  "action": "play",
  "card_id": 812,
  "target_id": 44
}
```

| Поле | Обязательность | Кто решает |
|---|---|---|
| `turn` | Всегда | - |
| `request_id` | Всегда | - |
| `action` | Всегда. Всегда ровно одно значение: `play` | - |
| `card_id` | Всегда | Игрок выбирает карту из `available` |
| `target_id` | Только если карта просит цель | Игрок выбирает из списка, который прислал сервер |

**Игрок оперирует картами, а не механиками.** Словаря механик на клиенте
нет вообще: названий вроде `MOVE_TO_STABLE` в запросе не бывает, клиент их
не знает и не показывает. Он нажал «сыграть» - дальше сервер сам смотрит на
карту, решает, куда она ложится, сколько карт с ней связано и на какую
позицию, и применяет всё сам.

Одно значение `action` вместо двадцати названий - это не экономия. Клиент
иначе пришлось бы держать копию правил и знать, какая механика что делает.
Словарь механик остаётся в базе как `mechanic_name_enum`: там он и нужен,
проверяющему коду, а не клиенту.

Новые механики в базе не ломают контракт: клиент по-прежнему шлёт
`play` и `card_id`, а что именно сделает карта, решает сервер.

### Что сервер разрешает

`available` - это список карт, которые сейчас можно сыграть. Не пары
«карта плюс механика», а просто карты: игрок выбирает из них.

Клиент не знает правил и не решает, что законно. Сервер считает доступные
карты из состояния хода и механик в стойлах и кладёт их в снимок. Клиент
рисует ровно этот список и отправляет назад только то, что в нём есть.

Когда карте нужна цель, сервер говорит об этом прямо в том же списке:

```json
"available": [
  { "card_id": 812, "needs_target": false },
  { "card_id": 905, "needs_target": true,
    "targets": [ { "id": 44, "label": "Стойка Ани" } ] }
]
```

Без этого флага клиент не отличил бы «сыграть без цели» от «сыграть, но
сначала спросить». Спрашивать всегда было бы неправильно: большинство карт
цели не требуют, и лишний вопрос перед каждым ходом раздражает.

Проверка живёт в SQL, а не в коде сервера - тогда любая дырка в разборе
JSON остаётся дыркой в парсере, а не способом сжульничать.

### Как механики применяются

Механики карты делятся на два вида. Разовые срабатывают при выкладывании.
Постоянные работают, пока карта лежит в стойке, и срабатывают сами - при
начале хода её владельца, при разборе стоек, при подсчёте победителя.

Карта с несколькими механиками отрабатывает все применимые **один раз** за
выкладывание. Дальше то, что осталось в стойле, живёт по своим правилам
дальше. Выбрать одну механику из нескольких нельзя: игрок выбирает карту,
а не отдельное свойство карты.

### Если событие не прошло

```json
{ "error": "операция_невозможна", "message": "нет места в стойле" }
```

Одно событие - одна транзакция: либо применилось, либо состояние не
изменилось совсем. Причина приходит текстом, чтобы игрок увидел, что
именно не вышло.

### Повторы и защита

`turn` и `request_id` ловят две разные беды. Двойной клик отклоняется по
несовпадению `turn`: ход уже другой. Ретрай после моргнувшего соединения
отклоняется по повтору `request_id`. Номера обработанных `request_id`
лежат в кэше; при потере кэша защита от ретраев ослабевает, но проверка
`turn` остаётся, потому что она в базе.

### Начало хода: разбор стойл

`end` не просто закрывает ход, а открывает следующий. Порядок важен.

1. `sp_resolve_stable_effects` - пересчёт, независимый от очереди.
   `PROTECT_STABLE`, `RESTRICT_CARD_PLAY` и `COUNT_AS_UNICORN`
   пересчитываются у всех. Счётчики длительности уменьшаются **только за
   действительно сыгранные ходы**, иначе чужой обрыв связи тратил бы всем
   защиту, а она конечная.
2. `sp_begin_turn` - выбор игрока. Проверка пропуска стоит **между**
   заходами: сначала выбрали игрока, потом посмотрели на пропуск.
3. `sp_fire_turn_start` - триггеры срабатывают **только у того, чей ход
   действительно открывается**. У пропущенного хода триггеры не идут, иначе
   в партии с отвалившимся игроком карта в его стойле срабатывала бы
   бесконечно.

Пропуск одноразовый: метка снимается, ход пропущенным не считается.
Пропуски подряд считаются - иначе двое, пропускающие друг друга по кругу,
закрутят партию навсегда.

**Механика упала - пропускаем её, пишем в лог и идём дальше.** Ход всё
равно открывается. Откат из-за одной сломанной карты заблокировал бы
партию навсегда, а такая карта может попасть в стойло в любой момент.

### Сброс

Отдельного запроса на сброс нет. Если в конце хода рука переполнена,
лишние карты уходят в сброс сами. Игрок выбирает, что сбросить, последним
`event` с `mechanic` = `DISCARD_FROM_HAND`.

## Справочник

| Метод | Путь | Возвращает |
|---|---|---|
| GET | `/api/catalog` | Все шаблоны карт: `{ id, name, description, img_link, mechanics }`, где `mechanics` - список названий |
| GET | `/api/mechanics` | Все механики: `{ code, name, description }` |

Полей `cost` и `stamina` в базе нет - в таблице `card_templates` только
`card_name`, `card_description` и `img_link`. Количество карт в колоде
тоже не хранится: это число строк в `cards` конкретной партии.

Читается один раз при загрузке и кэшируется клиентом.

## События SSE

Общий поток: `GET /api/events`. Один на сессию, **без `{game_id}`**.

| Метод | Путь | Что это |
|---|---|---|
| GET | `/api/events` | Поток состояния |

Один поток на пользователя, а не на партию. Он несёт и лобби, и состояние
партии, поэтому при входе в другую партию переподключаться не нужно -
клиент просто рисует пришедшее.

```
event: game_state
data: { "game": {...}, "your_turn": true, "turn": 12,
        "available": ["MOVE_TO_STABLE", "DRAW_FROM_DECK"] }
```

**Событие одно, и оно шлётся при любом изменении.** Отдельных событий
про карты, ходы и вступления нет: клиенту не нужно знать, что именно
случилось, чтобы нарисовать поле. Сказали, нажали, отработало - пришло
состояние.

Состояние всегда полное, а не дельта. Иначе клиенту пришлось бы держать
свою копию игры и уметь её чинить, а при обрыве - ещё и догонять
пропущенное. Полный снимок проще: сломалось - перерисовалось.

Побочный плюс: новое правило или новая механика не требует новых событий.
Появилась карта с новым поведением - она просто попала в снимок.

Что отличается у разных игроков, так это `available` и `your_turn`: это
считается под каждого, кому сервер шлёт снимок. Остальное состояние
одинаковое.

**Событий с `id` нет, и `Last-Event-ID` тоже.** Событие всегда полный
снимок, поэтому переподключившемуся не нужно догонять историю: он просто
получает текущее состояние. Хранить номера событий, чтобы отдать дельту, -
значит держать в базе то, что клиенту не нужно. Единственное, что стоит
у потока, - это `Content-Type: text/event-stream`.

Исключение того, кто инициировал действие, здесь **не делаем**: он всё
равно получает свой результат в поток, а дублирующий снимок ему безвреден.
Зато правило «кому не слать» - лишнее место, где можно ошибиться и потерять
чужое обновление.

Раз в 25 секунд сервер шлёт пустой комментарий-пинг, чтобы провайдер и
прокси не рвали соединение по таймауту.

Раз партии общих endpoint для чтения нет вообще: `discard`, `stables` и
`deck` отдавать не нужно, потому что весь этот состав уже лежит в снимке.
Отдельные запросы существовали бы только для того, чтобы заново узнать то,
что клиент и так получил секунду назад.

## Админка

Требует роль `admin` в сессии, иначе 403. Роль приходит из токена
провайдера при входе и хранится в кэше.

Карта - это картинка, описание и набор механик. Хранится один раз в
`card_templates`. Экземпляры карт внутри партии ссылаются на шаблон,
поэтому одна карта описана один раз на всю систему.

| Метод | Путь | Отвечает | Ошибки |
|---|---|---|---|
| GET | `/api/admin/cards` | `200` `{ items: [...], total }` | 401, 403 |
| POST | `/api/admin/cards` | `201` `{ template_id }` | 401, 403, 409 |
| PATCH | `/api/admin/cards/{template_id}` | `200` `{ template }` | 401, 403, 404 |
| PUT | `/api/admin/cards/{template_id}/mechanics` | `200` `{ mechanics }` | 401, 403, 404, 422 |
| GET | `/api/admin/mechanics` | `200` `{ id, name, type }` | 401, 403 |
| POST | `/api/admin/games/{game_id}/cards` | `200` `{ added }` | 401, 403, 404, 409 |

Параметры есть только у `GET /api/admin/cards`:

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `q` | - | Поиск по имени и описанию, нечувствительный к регистру |
| `mechanic` | - | Только карты с этой механикой по `id` |
| `limit` | `50` | Сколько вернуть, максимум 200 |
| `offset` | `0` | Сколько пропустить |

Поиск и фильтр по механике - не удобство, а necessity: без них список
шаблонов на несколько сотен позиций искать руками.

**Про `PUT .../mechanics`.** Список заменяется целиком, а не добавляется.
Так клиенту не нужно знать, что уже было привязано, и не нужны отдельные
`POST` и `DELETE` для привязки.

**Про создание карты.** Ссылка на картинку уникальна, повтор даёт 409.
`POST` отвечает 201, потому что это создание нового ресурса, а не изменение
существующего. Остальные пишущие отвечают 204 или 200.
Новую механику создать нельзя: справочник зашит в базу, пополняется
только миграцией.

**Про `/api/admin/games/{game_id}/cards`.** Добавляет в колоду партии
экземпляры карты. Работает только пока партия не началась, иначе 409.
Без этого эндпоинта колода партии наполнялась бы только при старте.

**Удаления нет.** Экземпляры карт ссылаются на шаблон с запретом удаления,
поэтому шаблон, попавший хотя бы в одну партию, удалить не получится.
Чистка - миграцией.

**Побочный эффект правки.** Экземпляры ссылаются на шаблон, а не копируют
его. Значит правка шаблона видна во всех партиях, где карта уже роздана,
включая идущие. Если это не устраивает, нужна блокировка правок, пока
есть незавершённые партии с этим шаблоном.

## Кэш

Всё в памяти процесса. Потеря не страшна.

| Ключ | Что хранит | Зачем |
|---|---|---|
| `session:{sid}` | `user_id` и роль `user` или `admin` | Не искать пользователя в базе на каждый запрос |
| `game:{id}:lobby` | Состав до старта, кто готов | Лобби живёт минуты, хранить в базе незачем |
| `game:{id}:turn` | Какой ход открыт, чей он | Читается на каждый запрос |
| `game:{id}:conns` | Открытые SSE-подключения | Раздавать события |
| `game:{id}:last_seen` | Когда клиент последний раз получил ответ | Отслеживать обрывы |

Что в кэше **не** лежит: карты, очки, кто выбыл. Это всё должно переживать
перезапуск сервера, значит только база.

Несколько экземпляров сервера: каждый держит свой кэш. События из базы
(`pg_notify`) раздаёт всем, поэтому все экземпляры разошлют событие своим
клиентам. Дубликатов не будет - событие придёт из базы один раз.

### Запись

| Функция | Что делает | Ошибки при нарушении правил |
|---|---|---|
| `sp_create_game(id_user, name, max_players, password)` | Создаёт партию, выдаёт место и карты | - |
| `sp_join_game(id_user, id_game, password)` | Пускает в партию и выдаёт карты. Если за игроком уже есть место, пускает обратно даже после старта, но руку выдаёт пустой - карты ушли в сброс | пароль неверный, нет свободного места, партия началась и это не возврат на своё место |
| `sp_leave_game(id_player, id_game)` | Убирает игрока из лобби или сбрасывает его руку в игре. Место в обоих случаях остаётся за ним | - |
| `sp_update_game(id_game, id_user, name, max_players, password)` | Меняет настройки партии. Только создатель и только до старта. `max_players` нельзя сделать меньше занятых мест, `password` можно обнулить через `null` | не создатель, уже началась, меньше занятых мест |
| `sp_cancel_game(id_game, id_user)` | Отменяет партию и удаляет её со всем содержимым. Только создатель и только до старта | не создатель, уже началась |
| `sp_set_game_password(id_game, password)` | Ставит пароль на партию до старта. Требует роль админа, проверяет сервер | не админ, уже началась |
| `sp_start_game(id_game)` | Проверяет готовность, раздаёт, открывает первый ход | не все готовы, мало карт |
| `sp_resolve_stable_effects(id_game)` | Пересчитывает у всех `PROTECT_STABLE`, `RESTRICT_CARD_PLAY` и `COUNT_AS_UNICORN`. Не завязан на очередь. Счётчики длительности уменьшаются только за сыгранные ходы. Упавшая механика пропускается и пишется в лог | нет, кроме сбоя отдельной механики - он не мешает ходу открыться |
| `sp_fire_turn_start(id_player)` | Срабатывают `TRIGGER_ON_TURN_START` у стойл указанного игрока. Вызывается только если его ход не пропущен | нет, кроме сбоя отдельной механики - она пропускается и пишется в лог |
| `sp_begin_turn(id_game)` | Выбирает следующего по счётчику игрока. Если его ход помечен пропуском, снимает метку, пропуск не считается сыгранным и триггеры не запускаются. Иначе вызывает `sp_fire_turn_start` и собирает список доступных операций. Считает пропуски подряд | ход уже открыт, все ходы пропущены подряд |
| `sp_apply_event(id_game, turn, request_id, event)` | Применяет одно событие игрока: по `action` и `card_id` сам находит механики карты, решает куда её класть и какие ещё аргументы нужны, применяет все разовые механики разом. Транзакция одна, проверяет против состояния, откатывает всё при ошибке | не его ход, номер хода не совпал, карта не в `available`, цель не из списка, повтор request_id |
| `sp_end_turn(id_game)` | Закрывает ход, сбрасывает лишние карты, увеличивает счётчик ходов игрока, затем пересчитывает стойки и открывает следующий ход. Главная точка входа для `POST /end` | не его ход, нельзя завершить |
| `sp_skip_turn(id_game)` | Пропускает ход отсутствующего игрока | ход открыт у игрока на связи |

## Правила, которые живут в базе

- Все проверки - внутри функций записи. Клиент может прислать что угодно,
  решение принимает база.
- Запись всегда в транзакции и всегда с блокировкой строки партии:
  два игрока не могут одновременно сыграть карту.
- Один вызов `POST /event` - одно событие и одна транзакция.
- Клиент не знает ни одного названия механики. Он выбирает карту и,
  если сервер попросил, цель.
- Порядок вызовов на ход: `sp_apply_event` сколько угодно раз, затем
  `sp_end_turn`. Тот внутри себя зовёт `sp_resolve_stable_effects`,
  затем `sp_begin_turn`. Триггеры запускает `sp_fire_turn_start` внутри
  `sp_begin_turn` и только если ход не пропущен.
- Пропущенный ход не считается сыгранным: триггеры начала хода у
  этого игрока не срабатывают, счётчики длительности не уменьшаются.
- Механика, упавшая при разборе стойл, не откатывает начало хода:
  она пропускается и пишется в лог. Партия не должна вставать колом
  из-за одной карты.
