# Архитектура игры (Unstable Unicorns)

## 1. Принципы проектирования

**Режим разработки:** только документация. Код бэкенда и OpenAPI не требуются.

Ключевые принципы:

1. **Единственный источник истины** — PostgreSQL (схема `init.sql`, **не менять**).
2. **Все SQL-операции идут только через веб-сервер.** Прямой доступ клиента к базе данных запрещён.
3. **Сервер-авторитетная архитектура** — все проверки, блокировки и переходы состояний на стороне сервера.
4. **Минимум колонки в БД, максимум логики в процедурах**. Если состояние живёт меньше одного хода — в памяти, если переживает перезапуск — в БД.
5. **Безопасность** — OIDC Authorization Code + PKCE, обязательный `sub` в формате UUID, сессия в `HttpOnly`/`Secure` cookie.
6. **Сериализация** — любые конкурентные действия проходят через `SELECT ... FOR UPDATE` по строке `games`.
7. **Дедупликация событий** — SSE использует идентификаторы событий, реконнект с `Last-Event-ID` и полным снапшотом.

## 2. Компонентная архитектура

Схема: `diagrams/01-architecture-components.mmd`.

Основные компоненты:

| Компонент | Назначение | Особенности |
|---|---|---|
| **SPA-клиент** | UI браузера | Без прямого доступа к PostgreSQL. Все запросы через REST/SSE |
| **Веб-сервер (backend)** | Авторитет | Единственная точка входа в БД. Вызывает только `sp_*`/`fn_*`. Хранит эфемерное состояние |
| **OIDC-провайдер** | Аутентификация | Абстрактный, Authorization Code + PKCE, `sub` формата UUID |
| **PostgreSQL** | Источник истины | ER-диаграмма не требуется. Только процедуры и функции |
| **SSE-хаб** | Уведомления | Рассылка через `pg_notify` + собственный поток событий |
| **Реестр присутствия** | Presence | In-memory или Redis. Эфемерный, восстанавливается после рестарта |

Детали — см. `diagrams/01-architecture-components.mmd`.

## 3. Аутентификация и сессии

### OIDC (Authorization Code + PKCE)

Схема: `diagrams/02-oidc-authorization-code-pkce.mmd`.

1. SPA генерирует `code_verifier` и `code_challenge` (S256).
2. Переход на Authorization Endpoint IDP с `code_challenge`, `state`, `nonce`.
3. Обмен кода на токены идёт **через веб-сервер**, без выдачи `access_token` в браузер (public client без секрета).
4. Валидация `id_token`: подпись по JWKS, `iss`, `aud`, `exp`, `nonce`. Кэш JWKS в памяти.
5. Единственное место, где появляется `user_id` — это `sub` из `id_token`. `sub` обязан быть в формате UUID.
6. Таблицы пользователей в БД нет. Идентификация игрока — по `user_id` (UUID) в `players`.

### Локальная сессия

- После успешного обмена кодом веб-сервер выставляет `HttpOnly`, `Secure`, `SameSite=Lax` cookie `sid`.
- Все REST-запросы и SSE проходят с этой cookie. EventSource автоматически её передаёт.
- Сессии хранятся в серверном хранилище (in-memory/Redis). При перезапуске сервера сессии теряются — клиент просто проходит логин повторно. Состояние игры при этом не теряется (оно в PostgreSQL).

## 4. API-контракт (REST + SSE)

### REST

Все операции над данными проходят только через веб-сервер и только путём вызова `sp_*`/`fn_*`. Прямого доступа к БД нет.

Типовой поток авторизованного запроса: `diagrams/03-authorized-api-request.mmd`.

Общие принципы:

- Ошибки возвращаются в формате с постоянным кодом (`ERR_*`), текст локализуем клиентом.
- Повторные запросы идемпотентны там, где это предусмотрено процедурами (PRIMARY KEY, проверки состояния).
- Все изменения идут в транзакциях, обязательна блокировка по `games` (`SELECT ... FOR UPDATE`).

### SSE (Server-Sent Events)

- Канал: `GET /api/games/{game_id}/events`
- Транспорт: EventSource, cookie передаётся автоматически.
- Идентификатор события: `id = moves.id_move` (там, где применимо). **Важно:** внутри одного хода несколько событий могут иметь одинаковый `id` — это нормальное явление.
- Реконнект: клиент передаёт `Last-Event-ID`. Сервер отдаёт пропущенные события через `fn_poll_changes`, при больших пропусках — полный **snapshot** (`fn_get_game_state`).
- Доставка: `pg_notify('game_events', ...)` используется для рассылки, но **не гарантирует доставку при переподключении и не переживает рестарт сервера**. Поэтому клиент всегда обязан уметь догонять изменения по курсору и перечитывать снапшот.
- Heartbeat: периодический ping для детектирования обрыва соединения.

События (из `fn_notify_state_changed`):

| Тип | Когда |
|---|---|
| `player_joined` | Занято место |
| `player_left` | Место освобождено |
| `game_started` | Партия начата |
| `turn_started` | Открыт новый ход |
| `cards_played` | Сыграна карта |
| `cards_moved` | Карты сменили зону |
| `turn_skipped` | Ход пропущен |
| `game_finished` | Партия завершена |

## 5. Игровые потоки

### Создание партии, вход, старт

`diagrams/04-game-create-join.mmd`.

1. `sp_create_game` создаёт партию, хозяин становится администратором, `move_status = false`.
2. Клиент подписывается на SSE, получает первый полный снимок.
3. Гости входят через `sp_join_game` после проверки пароля (`fn_check_game_password`). Порядок мест — `move_order`.
4. Хост запускает партию через `sp_start_game`. Сервер последовательно вызывает `sp_create_cards` и `sp_deal_cards` (5 карт каждому). Начинается первый ход — `sp_begin_turn`.

### Открытие хода и добор

`diagrams/05-turn-begin-and-draw.mmd`.

- Открытие хода: `sp_begin_turn`. Вставляет строку в `moves` (`move_number = max+1` по игроку), берёт 1 карту из колоды (неупорядоченный мешок: `ORDER BY random()`), кладёт в руку (`player_cards.is_public = false`), выставляет `move_status = true`.
- Фаза хода **не хранится в БД**. Фазы держатся в `p_parameters` сервера и перепроверяются в каждой процедуре.
- Текущий игрок определяется не по колонке, а по **максимальному числу ходов** в `moves`, при открытом ходе (`move_status = true`).

### Сыгрыш карты

`diagrams/06-play-card.mmd`.

- Все действия проходят с блокировкой `games FOR UPDATE` — единственная точка сериализации.
- `sp_play_card` определяет механику карты, вызывает `sp_move_card` для смены зоны (рука → стойло: `is_public` меняется с `false` на `true`).
- Триггеры, связанные с картой, срабатывают в той же транзакции.
- После каждого хода вызывается `fn_check_victory`. При победе рассылается `game_finished`.

### Завершение хода и передача

`diagrams/07-end-turn-and-elimination.mmd`.

- `sp_end_turn` проверяет, что рука ≤ `HAND_LIMIT`. При превышении игрок должен сбросить лишние карты через `sp_discard_from_hand` (по одной карте, как в процедуре).
- Закрытие хода переводит `move_status = false`. Следующий ход открывается серверным вызовом `sp_begin_turn`.
- **Выбывание игроков**: в `init.sql` нет `players.is_eliminated`. Признак выбывания не выводится из имеющихся данных. Поэтому до миграции он хранится в `p_parameters` сервера. После рестарта сервера посреди партии выбывшие считаются активными. Минимальное исправление — добавить колонку (см. раздел 7).

## 6. Надёжность, конкурентность, отказоустойчивость

### Отключение игрока и пропуск хода

`diagrams/08-disconnect-and-skip.mmd`.

- Присутствие игрока — в in-memory/Redis (колонок `last_seen` в схеме нет).
- При обрыве SSE соединение помечается как `suspect`, включается **grace-окно** переподключения (120 секунд). Если игрок вернулся с тем же `Last-Event-ID` — пропуск хода не происходит, изменения догоняются по курсору.
- Если grace-окно истекло, фоновый воркер вызывает `sp_skip_disconnected_turn`. Проверка отключения **разнесена**: вне транзакции — по реестру присутствия, **внутри транзакции** — перепроверка владельца открытого хода. Это исключает гонку (игрок мог переподключиться ровно в момент проверки).
- `sp_skip_disconnected_turn` идемпотентен: если ход уже перешёл другому игроку, возвращает `skipped = false`.

### Сериализация конкурентных действий

`diagrams/09-concurrent-actions.mmd`.

- **Единственная точка сериализации** — `SELECT ... FOR UPDATE` по строке `games(id_game)`.
- PostgreSQL отдаёт блокировку строго одному процессу, остальные встают в очередь. Порядок не зависит от того, кто нажал кнопку первым (клиентский тайминг не влияет).
- Все `sp_*`, изменяющие состояние, берут эту блокировку в начале транзакции.
- Проверки «текущий ли это игрок», «ход открыт ли», «партия в нужном состоянии» делаются **внутри транзакции** после захвата блокировки — защита от состояния гонки.
- Ошибки возвращаются с постоянными кодами (`ERR_*`), клиент не показывает SQLSTATE.

### Победа и конец партии

`diagrams/10-endgame-and-victory.mmd`.

`fn_check_victory` проверяет три условия завершения:

1. **Достигнут порог единорогов.** Для 2–5 игроков — 7, для 6 игроков — 6. Единорог — карта с механикой `COUNT_AS_UNICORN`. Правило определения: карта считается единорогом, если описание не говорит иного. Это правило выражено текстом, поэтому точный подсчёт ведётся на уровне логики (в бэкенде) по `card_name` — в чистом SQL без дополнительного поля оно невыразимо полностью.
2. **Колода опустела (endgame).** Если колода пуста (`deck_size = 0`), побеждает игрок с максимальным числом единорогов. При равенстве — сравнивается сумма длин названий карт-единорогов (`SUM(LENGTH(t.card_name))`). При полном равенстве — победителя нет.
3. **Остался один активный игрок.** Реализуемо только после добавления `players.is_eliminated` (см. раздел 7). До миграции проверка ведётся по реестру выбывших в `p_parameters`.

Результат победы хранится не в колонках (их нет), а пересчитывается `fn_check_victory` при каждом запросе состояния — переживает перезапуск сервера.

### Конечный автомат состояний

`diagrams/11-state-machine.mmd`.

Состояния не хранятся в БД как enum-колонка. Определяются комбинацией:

- `games.move_status` (ход открыт/закрыт)
- Наличие открытой строки в `moves`
- Число игроков, число карт в колоде
- Результат `fn_check_victory`

Фаза хода хранится **только** в `p_parameters` сервера.

## 7. Известные ограничения и предлагаемое расширение схемы

Схема `init.sql` не изменяется по условию задачи. Однако есть одно **непреодолимое ограничение**, которое не получается обойти без DDL.

### Выбывание игроков

В `init.sql` нет `players.is_eliminated`. Выбывание игрока не выводится из имеющихся данных (особенно в ситуации «остался один»). Поэтому:

- **До миграции:** выбывшие хранятся в `p_parameters` сервера. После рестарта сервера посреди партии выбывшие снова считаются активными.
- **После миграции (минимально):**

```sql
ALTER TABLE players
  ADD COLUMN is_eliminated BOOLEAN NOT NULL DEFAULT false;
```

Этого достаточно: `sp_leave_game` выставляет флаг, передача хода пропускает выбывших, `fn_check_victory` получает корректное условие «остался ровно один активный».

### Остальные механики

- `SHUFFLE_DECK` и `MOVE_TO_NURSERY` **осознанно без эффекта** (порядок колоды не хранится и не нужен, яслей нет).
- `PROTECT_STABLE`, `RESTRICT_CARD_PLAY`, `TRIGGER_ON_LEAVE_STABLE` **поддерживаются логикой бэкенда** и хранят своё состояние в `p_parameters` (живут один ход).
- `sp_set_ready` исключён — в упрощённых правилах фаза готовности не моделируется.
- `COUNT_AS_UNICORN` учитывается при подсчёте победы (правило частично текстовое).

## 8. Мониторинг, валидация, здоровье

- `fn_healthcheck` — проверка доступности БД.
- `fn_validate_game_integrity` — проверка целостности: карта не может быть одновременно в двух зонах, суммы должны сходиться, все ссылки валидны.
- Консистентность: все изменения только через транзакции, блокировка по `games`, проверки после захвата блокировки.
- Журналы: события в SSE, `cards_in_moves` хранит историю хода (журнал). `moves.id_move` используется как курсор для догоняния пропусков.
