# Каталог SQL-процедур

Все SQL-запросы к базе выполняет **только веб-сервер**. Клиент не имеет прямого
подключения к PostgreSQL. Ниже — полный перечень процедур и функций.

## Легенда

**Кто вызывает**

| Метка | Смысл |
|---|---|
| `клиент` | Процедуру дёргает клиент через REST-эндпоинт. Веб-сервер уточняет `id_player` по `user_id` из OIDC-токена и передаёт параметры дальше |
| `сервер` | Процедуру вызывает только веб-сервер из внутреннего кода. Эндпоинта для клиента нет |
| `воркер` | Фоновая задача по расписанию, вне пользовательского запроса |
| `внутр.` | Вызывается только из тела других процедур. Наружу не выставлена |

**Префиксы**

| Префикс | Смысл |
|---|---|
| `sp_` | Изменяет данные. Всегда вызывается внутри транзакции |
| `fn_` | Только читает. Может вызываться вне транзакции |

**Константы предметной области**

| Значение | Смысл |
|---|---|
| `MIN_PLAYERS = 2`, `MAX_PLAYERS = 6` | Размер партии. Верхняя граница задана `CHECK (number_of_players BETWEEN 0 AND 6)` |
| `HAND_LIMIT = 7` | Максимум карт на руке, фаза «Завершение хода» |
| `DEAL_COUNT = 5` | Карт на руке в начале партии |
| `WIN_UNICORNS_SMALL = 7` | Победа при 2–5 игроках |
| `WIN_UNICORNS_LARGE = 6` | Победа при 6 игроках |
| `THRESHOLD_KEEP` | Порог перехода: 5 или 6 игроков, вычисляется от фактического числа мест |

## 1. Лобби и партии

### `sp_create_game`

Создать партию и место хоста.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_owner_user_id` | `uuid` | да | `sub` из OIDC-токена хоста |
| `p_max_players` | `int` | да | Вместимость, `2..6`. Фиксируется один раз и не меняется |
| `p_is_private` | `boolean` | да | `true` — требуется пароль для входа |
| `p_game_password` | `varchar(512)` | нет | BCrypt-хеш пароля. Обязателен при `p_is_private = true` |

**Возвращает** `bigint` — `id_game`.

**Логика:** вставить `games (move_status = false, number_of_players = 1)`; вставить
`players (move_order = 1, is_admin = true)`; при приватной партии — вставить
строку в `passwords`.

**Ограничения:** `CHECK (number_of_players BETWEEN 0 AND 6)`; пароль не может
быть пустым.

---

### `fn_list_open_games`

Список партий, в которые можно зайти. Для экрана лобби.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_viewer_user_id` | `uuid` | да | Чтобы отметить партии, где игрок уже сидит |
| `p_limit` | `int` | да | `1..100` |
| `p_offset` | `int` | да | Постраничный сдвиг |

**Возвращает** таблицу: `id_game`, `max_players`, `seated_count`, `is_private`,
`has_seat`, `status`.

**Ограничения:** `status = 'waiting'` — ходов ещё не было. Если есть `moves` у хоста,
партия считается начавшейся и в лобби не показывается.

---

### `fn_get_game_brief`

Карточка партии для экрана ожидания. Карты не раскрываются.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_viewer_user_id` | `uuid` | да | Определяет `is_admin` и `has_seat` |

**Возвращает** `jsonb`: `id_game`, `status`, `max_players`, `is_private`,
`has_seat`, `is_admin`, список мест (`id_player`, `move_order`, `is_admin`, `card_count`).

**Ограничения:** функция **не должна** возвращать содержимое стойлов и рук —
это делает только `fn_get_game_state`.

---

### `fn_check_game_password`

Проверить пароль партии до попытки занять место.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_game_password` | `varchar` | да | Пароль, введённый пользователем |

**Возвращает** `boolean`.

**Логика:** если строки в `passwords` нет — партийная проверка не требуется.
Иначе сверяется BCrypt-хеш. Сравнение константного времени.

---

### `sp_join_game`

Занять место за столом.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_user_id` | `uuid` | да | `sub` из OIDC-токена |
| `p_game_password` | `varchar` | нет | Нужен, если партия приватная |
| `p_is_bot` | `boolean` | да | `true` — место занимает бот |

**Возвращает** `bigint` — `id_player`.

**Проверки:** партия ещё не началась; количество мест меньше `p_max_players`;
пароль совпал; `UNIQUE (id_game, user_id)` — игрок ещё не сидит.

**Логика:** вычислить `max(move_order) + 1`; вставить `players`; увеличить
`games.number_of_players`; выпустить `pg_notify`.

**Ограничения:** `UNIQUE (id_game, move_order)` защищает от двух игроков с одним
номером места.

---

### `sp_leave_game`

Выйти из партии.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_user_id` | `uuid` | да | Уходящий игрок |

**Возвращает** `void`.

**Проверки:** ход не открыт на уходящего игрока; это не последнее место, если
партия уже началась.

**Логика:** удалить место (каскад сносит `player_cards` и `moves`); перенумеровать
оставшиеся `move_order` с сохранением порядка; уменьшить `games.number_of_players`;
выпустить `pg_notify`.

**Замечание:** `ON DELETE RESTRICT` на `moves.id_player` не даст удалить игрока с
историей. Поэтому удаление возможно только пока партия в лобби. Это осознанное
ограничение — «уйти с середины партии» в упрощённых правилах не предусмотрено.

---

### `sp_set_ready`

**Процедура исключена из дизайна.**

В упрощённых правилах отдельной фазы готовности нет: партию запускает
администратор, когда мест достаточно. Флаг готовности потребовал бы колонки
`players.is_ready`, которой в `init.sql` нет, а эмулировать его через
`p_parameters` означало бы хранить игровое состояние в памяти.

Если полноценное лобби понадобится, добавьте одну колонку — процедура
восстанавливается тридцатью строками.

---

### `sp_set_game_password`

Сменить пароль партии.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_actor_user_id` | `uuid` | да | Кто меняет. Требуется `is_admin = true` |
| `p_game_password` | `varchar(512)` | нет | Новый хеш. `NULL` — снять пароль, сделать партию открытой |

**Возвращает** `void`.

**Логика:** `INSERT ... ON CONFLICT (id_game) DO UPDATE`, либо `DELETE` при снятии.

---

### `sp_start_game`

Начать партию: раздать карты, создать экземпляры карт из шаблонов.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_actor_user_id` | `uuid` | да | Только хост, `players.is_admin = true` |

**Возвращает** `void`.

**Проверки:** `players.is_admin`; мест не меньше `MIN_PLAYERS`; ни у кого ещё нет
ходов.

**Логика:** создать по одному `cards` на каждый `card_templates`; взять
`DEAL_COUNT` случайных карт в руку каждого игрока (`is_public = false`);
остальные формируют колоду.

**Ключевое:** колода **не требует порядка** — розыгрыш идёт случайным выбором.
Поэтому позиции в колоде не хранятся и не нужны.

**Замечание о порядке выдачи:** `SELECT ... FROM cards ORDER BY random() LIMIT 5`
выдаёт разные карты разным игрокам, но внутри одной выборки `ORDER BY random()`
не даёт гарантии уникальности строк между игроками. Корректный вариант —
выбрать случайное смещение один раз на партию и раздать с него по кругу:

```sql
SELECT c.id_card
  FROM cards c
  JOIN games g ON g.id_game = c.id_game
 WHERE c.id_game = p_game_id
 ORDER BY c.id_card
 OFFSET floor(random() * (SELECT count(*) FROM cards WHERE id_game = p_game_id))
 LIMIT p_total_to_deal;
```

Затем выданные id раздаются игрокам по кругу. Это гарантирует отсутствие дублей.

## 2. Игровой цикл

### `fn_get_game_state`

Полный снимок состояния партии для клиента. **Основное место чтения.**

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_viewer_user_id` | `uuid` | да | Чья рука раскрывается |

**Возвращает** `jsonb`:

| Поле | Содержимое |
|---|---|
| `status` | `waiting` \| `playing` \| `finished` |
| `turn` | `current_player_id`, `move_order`, `is_your_turn`, `turn_seq` |
| `hand` | Карты **только** `p_viewer_user_id`. Для остальных — лишь счётчик |
| `stables` | Все стойло игроков, публично, с составом и количеством единорогов |
| `deck` | Только `count`. Состав скрыт |
| `discard` | Публично, по `position` |
| `events` | Ходы за последние N |
| `winner` | `id_player` или `null` |

**Безопасность:** рука возвращается строго по `WHERE pc.id_player = (place of p_viewer_user_id)`.
Отдельной проверки на сервере недостаточно — ограничение должно быть в самом SQL,
иначе утечка проявится при будущем изменении запроса.

### `fn_get_legal_actions`

Что игрок может сделать прямо сейчас. Для отрисовки кнопок.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Место, выведенное сервером из токена |

**Возвращает** `jsonb`: `can_draw`, `can_play`, `can_end_turn`, `can_skip`,
список доступных карт с допустимыми целями.

**Замечание:** это подсказка для интерфейса, **не граница безопасности**.
Граница — проверки внутри `sp_play_card` и остальных `sp_`.

### `sp_begin_turn`

Открыть ход: вычислить текущего игрока и выложить его начальную раздачу.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_actor_user_id` | `uuid` | нет | Кто инициировал. `NULL` — хост, автоматически |

**Возвращает** `void`.

**Проверки:** `move_status = false` — ход не открыт; число мест достигло
`MIN_PLAYERS`.

**Логика:**

1. Определить текущего игрока. Единственный признак открытого хода —
   `games.move_status`. Игрок, чей ход открыт, — это игрок с **максимальным
   числом строк в `moves`**: пока ход идёт, он опережает остальных ровно на один
   свой ход, и максимум всегда единственный. Для первого хода это игрок с
   `move_order = 1`.
2. Вставить `moves (id_player, move_number)`, где `move_number` — `max + 1` по
   этому игроку. Ограничение `uq_player_move` страхует от повторной вставки.
3. Выложить на руку `start_cards` из `p_parameters`.
4. Проставить `move_status = true`.

**Важно:** колонки `closed_at` в `moves` нет, поэтому «ход открыт» определяется
только флагом `move_status`, а не состоянием строки в `moves`. См. раздел 5.

**Параметры по умолчанию в `p_parameters`:**

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `start_cards` | `1` | Карт добирается в начале хода |
| `draw_cards` | `1` | Карт обязательно добирается в фазе добора |

Разделение нужно для режима вдвоём, где добор может быть добровольным.

**Ограничение:** полагается на `SELECT ... FOR UPDATE` строки `games`, поэтому
вызов из нескольких воркеров безопасен — второй увидит `move_status = true` и
отклонится.

---

### `sp_draw_cards`

Фаза «Добор». Взять карты из колоды.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Место из токена |

**Возвращает** `jsonb`: список выбранных `id_card`.

**Проверки:** `move_status = true`; `id_player` — текущий игрок; колода не пуста;
после добора размер руки не превышает `HAND_LIMIT`.

**Логика:** `SELECT id_card FROM cards WHERE id_game = $1 AND id_card NOT IN
(player_cards) AND id_card NOT IN discard ORDER BY random() LIMIT n`; создать
`player_cards` с `is_public = false`; записать в `cards_in_moves`.

**Ошибки:** `ERR_GAME_DECK_EMPTY` — колода кончилась, переход к проверке победы.

---

### `sp_play_card`

**Ядро игры.** Сыграть карту с руки.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Место из токена |
| `p_card_id` | `bigint` | да | Карта на руке |
| `p_target_player_id` | `bigint` | нет | Цель. Для `DESTROY_IN_STABLE`, `STEAL_FROM_STABLE`, `RESTRICT_CARD_PLAY` |
| `p_target_card_id` | `bigint` | нет | Конкретная карта цели |
| `p_parameters` | `jsonb` | нет | Параметры эффекта |

**`p_parameters` для двойных карт.** В базовом наборе есть карты «Сunyверсальный
доктор» и «Добрый доктор» с параметром `amount` (по умолчанию 2), и «Большой
покровитель» с `target_type`:

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `amount` | `int` | `2` | Сколько карт затронуть |
| `target_type` | `text` | `'self'` | `self` \| `target` \| `both` |

**Возвращает** `jsonb`: `ok`, `state_delta`, `pending_effects`.

**Проверки:** фаза хода; карта в руке игрока; карта не `is_public`; количество
карт на руке ≤ `HAND_LIMIT`; для целевых механик — цель валидна и не защищена
(`PROTECT_STABLE`); нет блокировки `RESTRICT_CARD_PLAY`.

**Логика:** определить механику через `template_mechanics`; заблокировать строку
`games` через `FOR UPDATE`; применить перемещение карты; записать в
`cards_in_moves`; сработать `TRIGGER_ON_ENTER_STABLE` и `TRIGGER_ON_LEAVE_STABLE`;
проверить победу.

**Сериализация:** `FOR UPDATE` на строке партии делает процедуру безопасной при
одновременных вызовах — второй дождётся и увидит уже изменённое состояние.

### `sp_move_card`

**Универсальное перемещение карты между зонами.** Обслуживает большинство механик.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_card_id` | `bigint` | да | Карта |
| `p_from_zone` | `text` | да | `hand` \| `stable` \| `deck` \| `discard` |
| `p_to_zone` | `text` | да | Куда перемещается |
| `p_player_id` | `bigint` | да | Владелец для `hand` и `stable` |
| `p_move_id` | `bigint` | да | Ход для записи в `cards_in_moves` |
| `p_position` | `int` | нет | Позиция в сбросе. `NULL` — следующая свободная |

**Возвращает** `jsonb`.

**Соответствие зон и строк:**

| Зона | Где хранится | Код |
|---|---|---|
| `hand` | `player_cards` с `is_public = false` | удалить из `discard`, upsert в `player_cards (false)` |
| `stable` | `player_cards` с `is_public = true` | то же, но `is_public = true` |
| `discard` | `discard` | удалить из `player_cards`, upsert в `discard` |
| `deck` | ничего | удалить из `discard` и `player_cards` |

**Ограничения:** карта не должна оказаться в двух зонах. На уровне схемы это не
защищено — поддерживается дисциплиной всех `sp_*`. Диагностика — `fn_validate_game_integrity`.

**Ошибки:** `ERR_CARD_ZONE_CONFLICT`, `ERR_CARD_NOT_IN_ZONE`.

### `sp_discard_from_hand`

Фаза «Завершение хода». Сбросить лишние карты с руки.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Место из токена |
| `p_card_id` | `bigint` | да | Карта с руки |

**Возвращает** `jsonb`.

**Проверки:** ход открыт и принадлежит игроку; карта на руке; фактический размер
руки **строго больше** `HAND_LIMIT` — иначе сброс незаконен.

**Логика:** `sp_move_card` в зону `discard` с позицией `max(position) + 1`.

---

### `sp_end_turn`

Завершить ход и передать его следующему игроку.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Место из токена |

**Возвращает** `jsonb`: `next_player_id`, `skipped`.

**Проверки:** ход открыт и принадлежит игроку; размер руки ≤ `HAND_LIMIT`;
не осталось неразрешённых обязательных эффектов.

**Логика:** увеличить счётчик ходов текущего игрока в журнале (тот же
`INSERT INTO moves`, что и в `sp_begin_turn`, со следующим `move_number`);
поставить `move_status = false`. Следующий ход открывает уже сервер отдельным
вызовом `sp_begin_turn`.

**Замечание:** `sp_skip_turn` и `sp_end_turn` **не отличаются по записи в базу**.
Различие только в проверках и в том, кто имеет право их вызвать: вручную —
только текущий игрок через REST, фоново — только сервер по истечении grace-окна.
Хранить признак «ход был пропущен» негде: в `moves` нет такой колонки, поэтому
факт пропуска передаётся клиентам событием `turn_skipped` и остаётся в памяти
сервера в пределах сессии игры.

---

### `sp_skip_turn`

Пропустить ход игрока. Механика `SKIP_PLAYER_TURN`.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Чей ход пропускается |
| `p_reason` | `text` | да | `manual` \| `disconnected` \| `effect` |

**Возвращает** `void`.

**Проверки:** ход открыт; это ход именно `p_player_id`; нет неразрешённых
эффектов.

**Логика:** записать `moves` с признаком пропуска; сдвинуть курсор хода;
`move_status = false`; `pg_notify` с событием `turn_skipped`.

**Ошибки:** `ERR_NOT_CURRENT_PLAYER`, `ERR_TURN_NOT_OPEN`.

---

### `sp_skip_disconnected_turn`

Пропустить ход игрока, у которого истекло окно переподключения.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_user_id` | `uuid` | да | Считающийся отключённым |

**Возвращает** `jsonb`: `skipped`, `current_player_id`.

**Проверки:** ход открыт (`move_status = true`) и принадлежит именно этому
`user_id`.

**Логика:** делегирует `sp_skip_turn` с причиной `disconnected`.

**Где проверяется отключение.** Реестр присутствия живёт **в памяти сервера или
в Redis** — колонки `players.last_seen` в `init.sql` нет, и добавлять её мы не
можем. Поэтому проверка разнесена:

- **вне транзакции** — фоновый воркер берёт из реестра кандидатов, у которых
  истекло grace-окно;
- **внутри транзакции** — процедура **перепроверяет, что ход всё ещё открыт и
  всё ещё принадлежит этому игроку**. Это и есть защита от гонки: если игрок
  успел переподключиться и сыграть ход раньше, чем воркер добрался до базы,
  `move_status` окажется иным либо текущим игроком будет уже другой, и
  `skipped` вернётся `false`.

**Защита от повторного пропуска:** процедура идемпотентна. Если ход уже перешёл
к следующему игроку, возвращается `skipped = false`, ничего не меняется.

**Что не проверяется в БД:** сам факт истечения grace-окна. Он достоверен ровно
настолько, насколько достоверен реестр присутствия. Взамен исключается
пропуск хода живого игрока — цена приемлемая.

## 4. Справочник, поиск, эффекты, победа, события

### `fn_get_catalog`

Справочник шаблонов карт и их механик. Отдаётся один раз при загрузке клиента.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_lang` | `varchar(8)` | да | `ru` \| `en` |

**Возвращает** таблицу: `id_card_template`, `card_name`, `card_description`,
`img_link`, `mechanics` (`text[]` значений enum).

**Особенность:** данные статичны, поэтому веб-сервер кэширует результат и
отдаёт клиенту с `ETag`. Процедура читает только `card_templates`,
`mechanics`, `template_mechanics`.

**Замечание:** в `init.sql` нет ни поля типа карты, ни флага «в колоде». Поэтому
справочник возвращает **все** шаблоны, а бэкенд решает, какие показывать в
интерфейсе. Это же делает механику добора неоднозначной: подходит ли подходящая
карта в колоду, определяет бэкенд, а не SQL — см. `sp_search_zone`.

---

### `sp_search_zone`

Поиск карты в колоде или сбросе по механике. Механики `SEARCH_IN_DECK`,
`SEARCH_IN_DISCARD`.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_zone` | `text` | да | `deck` \| `discard` |
| `p_mechanic` | `mechanic_name_enum` | да | Искомая механика |
| `p_limit` | `int` | да | Сколько кандидатов показать |

**Возвращает** `TABLE(id_card bigint, id_card_template bigint, card_name text, position int)`.

**Логика:**

- `deck` — карты партии, которых нет ни в `player_cards`, ни в `discard`.
- `discard` — строки `discard`, отсортированные по `position`.

**Важно:** результат **детерминирован**. Порядок задаётся явно: для колоды
`ORDER BY id_card`, для сброса `ORDER BY position`. Это позволяет на следующем
шаге проверить, что взятая карта действительно входила в показанный набор,
без хранения состояния «что было раскрыто» — в `init.sql` для этого нет ни
таблицы, ни колонки.

**Возвращает** `jsonb`.

**Проверки:** это текущий ход игрока; карта существует; карта входит в

### `sp_resolve_effect`

Подтвердить или отклонить отложенный эффект.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_player_id` | `bigint` | да | Владелец эффекта |
| `p_move_id` | `bigint` | да | Ход, породивший эффект |
| `p_card_id` | `bigint` | нет | Карта, участвующая в эффекте |
| `p_accept` | `boolean` | да | `true` — применить, `false` — пропустить |

**Возвращает** `jsonb`.

**Проверки:** эффект ещё не разрешён; эффект принадлежит этому игроку; для
обязательного эффекта `p_accept` игнорируется и всегда `true`.

**Замечание:** очередь отложенных эффектов в `init.sql` хранить негде. Эффекты
восстанавливаются из `cards_in_moves` и `moves` — то есть по факту уже
применённые считаются разрешёнными, а невыполненные обязательные эффекты
**не могут быть восстановлены**. Поэтому в упрощённых правилах цепочки «затем»
не реализованы, и процедура используется только для подтверждения выбора цели
в рамках одного хода. Полноценная очередь требует отдельной таблицы.

### `fn_check_victory`

Проверка условия победы.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |

**Возвращает** `TABLE(status text, winner_player_id bigint, detail jsonb)`.

**Логика:**

1. Посчитать число мест. При `≤ 5` порог — `WIN_UNICORNS_SMALL`, при `6` —
   `WIN_UNICORNS_LARGE`.
2. Сосчитать единорогов в каждом стойле. Признак единорога — наличие механики
   `COUNT_AS_UNICORN` у шаблона, с поправкой на исключения, описанные
   текстом правил (см. раздел 4).
3. Если порог достигнут — победа игрока.
4. Иначе, если колода пуста — побеждает игрок с максимумом; при равенстве
   сравнивается сумма длин названий карт-единорогов; при полном равенстве
   победителя нет, все проигрывают.

**Замечание:** правило «сумма букв в названиях» считается как
`SUM(LENGTH(t.card_name))` по единорогам в стойле. Это воспроизводимо в SQL
без дополнительных данных.

### `fn_notify_state_changed`

Рассылка события игрокам.

| Параметр | Тип | Обяз. | Назначение |
|---|---|---|---|
| `p_game_id` | `bigint` | да | Партия |
| `p_event_type` | `text` | да | Тип события |
| `p_payload` | `jsonb` | да | Полезная нагрузка |

**Возвращает** `void`.

**Логика:** `PERFORM pg_notify('game_events', jsonb_build_object(...))`.

**Типы событий:**

| Тип | Когда |
|---|---|
| `player_joined` | Занято место |
| `player_left` | Место освобождено |
| `game_started` | Партия начата |
| `turn_started` | Открыт новый ход |
| `cards_played` | Сыграна карта |
| `cards_moved` | Карты сменили зону |
| `turn_skipped` | Ход пропущен |
| `game_finished` | Партия завершена |

**Замечание:** `pg_notify` **не гарантирует доставку** при переподключении
клиента и не переживает перезапуск бэкенда. Поэтому SSE-поток всегда
сопровождается возможностью полного перечитывания состояния через
`fn_get_game_state`, а пропущенные события — через курсор по `moves`.

## 5. Ограничения и допущения

### Принцип: где живёт состояние

| Тип состояния | Где хранится | Почему |
|---|---|---|
| Состояние партии | **PostgreSQL** | Переживает перезапуск сервера, единственный источник истины |
| Состояние хода (фаза, отложенные эффекты, защита стойла, запрет на тип карт) | **`p_parameters` сервера**, в памяти или Redis | Живёт не дольше одного хода. Потеря при рестарте безопазна: ход просто начинается заново с начала |
| Присутствие игрока (он вкладку закрыл или нет) | **Реестр присутствия** | Эфемерно по определению. В БД этому места нет и не нужно |

Отсюда следствие: **всё, что должно пережить рестарт сервера, обязано быть в
таблицах `init.sql`.** Всё, что живёт один ход, — в памяти.

### Чего в `init.sql` нет и как это обойдено

| Чего не хватает | Как решено сейчас |
|---|---|
| Нет таблицы зон | Зона выводится из наличия строки в `player_cards` / `discard` |
| Нет порядка карт в колоде | Порядок не нужен: добор случайный. Колода — неупорядоченное множество |
| Нет порядка карт на руке | Порядок не нужен: рука скрыта и не упорядочивается |
| Нет порядка карт в стойле | Порядок правилами не важен |
| Нет `games.current_player_id` | Текущий игрок — тот, у кого максимум строк в `moves`; открытость хода — `games.move_status` |
| Нет `moves.closed_at` | Открытость хода определяется только флагом `games.move_status` |
| Нет `games.turn_phase` | Фаза в `p_parameters`, перепроверяется в каждой `sp_` на входе |
| Нет `players.last_seen` | Присутствие в реестре сервера; внутри БД перепроверяется только владелец открытого хода |
| Нет `players.is_ready` | Флаг готовности **не моделируется**: хост стартует партию, когда мест достаточно |
| Нет `players.is_eliminated` | **Не обходится. См. следующий раздел** |
| Карта может оказаться в двух зонах | Дисциплина `sp_move_card` плюс проверка `fn_validate_game_integrity` |
| `discard.position` без `UNIQUE` | Выдаётся под блокировкой строки партии, дубли невозможны |

### Выбывание игроков — единственное непреодолимое ограничение

Правила игры предполагают, что игрок, сбросивший руку и не имеющий единорогов,
**выбывает**, а его место пропускается. В `init.sql` нет ни одного поля, которое
это выражает, и — что важнее — **это не выводится из имеющихся данных**.

Проверка на «отстал по счётчику ходов» не работает: игрок, выбывший последним,
формально не отстаёт от остальных. А кодировать выбывание через `move_order`
нельзя — он нужен для порядка хода.

**Как живём до решения:** выбывание держится в `p_parameters` сервера. Это
означает, что после рестарта сервера посреди партии выбывшие игроки снова
считаются активными. Для тестовой сборки приемлемо, для продакшена — нет.

**Минимальная миграция, которая это чинит** (в набор поставки не входит, схема
не меняется):

```sql
ALTER TABLE players ADD COLUMN is_eliminated BOOLEAN NOT NULL DEFAULT false;
```

Одна колонка. После её добавления `sp_leave_game` начинает её выставлять,
передача хода — пропускать выбывших, а `fn_check_victory` получает третье
условие победы «остался один» без каких-либо переделок в логике.

**Все остальные функции при этом не меняются** — поэтому миграцию можно
выполнить позже, не переписывая код.

### Зоны в упрощённых правилах

| Зона | Статус |
|---|---|
| Колода | Есть. Неупорядоченное множество |
| Рука | Есть. `player_cards.is_public = false` |
| Стойло | Есть. `player_cards.is_public = true` |
| Сброс | Есть. Таблица `discard`, порядок важен для выбора карты |
| Ясли | **Отсутствуют.** Механика `MOVE_TO_NURSERY` не используется |
| Памятки | **Отсутствуют.** 8 памяток из оригинальных правил не реализованы |

### Покрытие механик из `Игра.md`

Все 20 атомарных механик поддержаны. Две сознательно не имеют эффекта, ещё две
живут в памяти сервера.

| Механика | Где реализована |
|---|---|
| `MOVE_TO_DECK` | `sp_move_card` |
| `MOVE_TO_HAND` | `sp_move_card` |
| `MOVE_TO_STABLE` | `sp_move_card`, `sp_play_card` |
| `MOVE_TO_DISCARD` | `sp_move_card`, `sp_discard_from_hand` |
| `MOVE_TO_NURSERY` | **Нет эффекта.** Яслей в упрощённых правилах нет |
| `DRAW_FROM_DECK` | `sp_draw_cards`, `sp_deal_cards` |
| `DISCARD_FROM_HAND` | `sp_discard_from_hand` |
| `SACRIFICE_FROM_STABLE` | `sp_move_card` с зоной `stable` → `discard`, цель — свой игрок |
| `DESTROY_IN_STABLE` | `sp_move_card` с зоной `stable` → `discard`, цель — чужой игрок |
| `STEAL_FROM_STABLE` | `sp_move_card` с зоной `stable` → `stable` чужого игрока |
| `SEARCH_IN_DECK` | `sp_search_zone` + `sp_search_take_card` |
| `SEARCH_IN_DISCARD` | `sp_search_zone` + `sp_search_take_card` |
| `SHUFFLE_DECK` | **Нет эффекта.** Порядок колоды не хранится, перемешивать нечего |
| `SKIP_PLAYER_TURN` | `sp_skip_turn`, `sp_skip_disconnected_turn` |
| `PROTECT_STABLE` | Логика в бэкенде, **состояние в `p_parameters`** |
| `RESTRICT_CARD_PLAY` | Логика в бэкенде, **состояние в `p_parameters`** |
| `TRIGGER_ON_TURN_START` | `sp_begin_turn` |
| `TRIGGER_ON_ENTER_STABLE` | `sp_play_card` |
| `TRIGGER_ON_LEAVE_STABLE` | `sp_play_card` |
| `COUNT_AS_UNICORN` | `fn_check_victory` |

**Почему `SHUFFLE_DECK` и `MOVE_TO_NURSERY` без эффекта.** Первое — следствие
решения сделать колоду неупорядоченным мешком: `Игра.md` предполагает
`deck_order`, но хранить порядок негде и не нужно, а случайный добор и так
равномерен. Второе — следствие того, что ясли исключены из упрощённых правил.
Оба решения приняты осознанно, а не по недосмотру.

**Почему `PROTECT_STABLE` и `RESTRICT_CARD_PLAY` живут в памяти.** Обе механики
по правилам действуют **до начала следующего хода владельца**. Жизненный цикл у
них — один ход, поэтому `p_parameters` достаточно, а постоянная колонка в
таблице `players` ради такого была бы лишней.

**Про `COUNT_AS_UNICORN`.** Правила считают карту единорогом, если её описание
не говорит иного. Это правило выражено **текстом**, а не полем, поэтому точный
подсчёт ведётся в бэкенде по `card_name`, который уже вернул `fn_check_victory`.
В чистом SQL без дополнительной таблицы правило невыразимо.
